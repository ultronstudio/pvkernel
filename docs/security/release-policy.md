# Release policy

pvKernel has three release classes. Each has different guarantees and a
different pipeline; this document is the authoritative description of
both. See also [docs/security/vulnerability-management.md](vulnerability-management.md)
for how a security finding feeds into a security release, and
[docs/security/github-configuration.md](github-configuration.md) for the
manual GitHub settings these pipelines depend on.

## Development build

Any commit on a feature branch or on `main`.

* No stability guarantee of any kind.
* Gated only by `.github/workflows/ci.yml` (format, clippy, build matrix,
  every deterministic QEMU scenario) and, where its trigger paths match,
  `.github/workflows/security.yml`.
* Not published as a GitHub Release or tag.

## Release candidate

Example: `v0.0.7-rc.1`, cut by `.github/workflows/release-candidate.yml`
(`workflow_dispatch` only - never automatic).

Requirements, enforced by the workflow itself:

* requested version is a bare `X.Y.Z` semantic version, and the RC number
  is a positive integer;
* `pvkernel-runner` and `kernel` package versions both already equal the
  requested version (workspace-inherited, see `Cargo.toml`
  `[workspace.package]`);
* `CHANGELOG.md` has a `## [X.Y.Z]` entry;
* the exact dated nightly toolchain (`rust-toolchain.toml`) resolves and
  is reported;
* `Cargo.lock` is committed;
* the target tag does not already exist;
* the full CI correctness gate (`ci.yml`, reused via `workflow_call`)
  passes;
* the full security gate (`security.yml`, reused via `workflow_call`)
  passes;
* every deterministic QEMU test passes (as part of the CI gate above).

Produces a GitHub **Pre-release**, explicitly marked as such, with:

* `pvkernel-<version>-rc.<N>.elf`
* `pvkernel-<version>-rc.<N>-uefi.img`
* `pvkernel-<version>.spdx.json` - an SPDX SBOM of the **workspace's
  build/source dependency graph** (generated by scanning the checked-out
  source tree and `Cargo.lock` before the release build runs), not a
  binary/package-level SBOM of the compiled ELF or UEFI image.
* `SHA256SUMS`
* `release-manifest.json`

All five files above are covered by the GitHub Artifact Attestation below
(its subject path is every file in the artifacts directory, not only the
two binaries), attested via GitHub Artifact Attestations (see
[docs/security/vulnerability-management.md](vulnerability-management.md)
and the final hardening report for exact verification steps).

An RC makes **no** stability claim and may contain release-blocking
defects - that is the point of cutting one before a stable release.

## Stable release

Example: `v0.0.7`, cut by `.github/workflows/release.yml`
(`workflow_dispatch` only).

Requirements, enforced by the workflow itself, on top of everything an RC
requires:

* the operator explicitly confirms the exact commit SHA being released,
  and the workflow verifies it matches the ref actually checked out
  (catches "dispatched against the wrong branch" operator error);
* the full CI and security gates run again against that exact commit
  (never promotes a different, unvalidated commit than what was checked);
* checksums, SPDX SBOM, release manifest, and artifact attestation are
  (re)generated from that exact build - never reused from a prior RC;
* a protected GitHub Environment named `release` must approve the
  `approval` job before `publish` runs (native GitHub Environment
  protection - see
  [docs/security/github-configuration.md](github-configuration.md) for
  the required manual configuration; this is **not** emulated with an
  `if:` actor check);
* there is no known unresolved release-blocking security issue (a
  judgment call made by whoever approves the `release` environment gate,
  informed by [docs/security/vulnerability-management.md](vulnerability-management.md)).

Produces a GitHub **stable Release** (not marked pre-release) with the
same artifact set as an RC, minus the `-rc.N` suffix.

A different commit than a previously-validated RC is never silently
promoted to stable: `release.yml` always reruns the full correctness and
security suite against whichever commit it is pointed at, rather than
reusing an RC's already-built artifacts.

## Security releases

A security release is a stable release (same pipeline, same artifact set)
whose release notes additionally disclose a fixed vulnerability once
coordinated disclosure allows it. Example: `v0.4.3`.

Release notes for a security release may contain a block like:

```text
Security

PVK-2029-0004
GHSA-xxxx-xxxx-xxxx
CVE-2029-xxxxx
CWE-xxx
CVSS v4.0: CVSS:4.0/...
```

Only identifiers that actually exist are ever included - never a
placeholder or a guessed CVE/GHSA/CWE/CVSS value (see
[docs/security/vulnerability-management.md](vulnerability-management.md)).

Security release notes clearly state:

* affected versions;
* the fixed version;
* impact, described at a level that does not hand over a working exploit
  during coordinated disclosure;
* required user action, if any;
* a workaround, if one exists and disclosure timing allows mentioning it.

Detailed exploit instructions are not published prematurely during
coordinated disclosure, consistent with
[SECURITY.md](../../SECURITY.md)'s coordinated-disclosure section.
